# PipiKKRescattering vs. LauRescatteringRes — 2026-09-14

Reproduction of `dynamics/lineshape/pipi_kk_rescattering.py`'s `convention="laura"`
branch against `LauRescatteringRes::amplitude` (Laura++ 3.8,
`Laura-3.8.0/Laura++/src/LauRescatteringRes.cc`), triggered by the question of
whether the two match closely enough to fit the `notebooks/benchmark/gen-3pi`
toys generated by that class. Python 3.14, JAX 0.11.1, CPU, x64.

## Method

A literal, line-by-line Python port of `LauRescatteringRes::amplitude`'s
"Rescattering" branch (the only branch it actually returns: the t-channel
term is written but commented out, and `RescatteringNoInter`'s `t<=s` zeroing
is a different, unused model) was evaluated at 43 mass points spanning
`0.85`-`1.90` GeV and compared to `PipiKKRescattering(convention="laura")`
with Laura's own constructor defaults (`lambdaPiPi=1.0`, `lambdaKK=2.8`,
`Mf=1.32`, `Ms=0.92`, `Mprime=1.5`, `Eps1=2.4`, `Eps2=-5.5`, `C0=1.3`,
`kaon_mass=LauConstants::mK=0.493677`), with the class's own mass window
disabled (`mass_min=0`, `mass_max=10`) so the raw formula could be compared
everywhere, not only inside the isobar fit's `1.0`-`1.5` GeV window.

## Before this change

Within `1.0`-`1.5` GeV (`Mprime=1.5` by default, coinciding with the window's
upper edge) the two already agreed to float64 precision, max `|diff|` over
that range `1.6e-16`. This is the range the `paper_isobar_benchmark*`
notebooks actually use, so their rescattering component was already correct.

Outside that range the two disagreed:

- Below `2*kaon_mass` (`0.85`-`0.975` GeV tested): Laura returns exactly zero
  (its explicit `eta0=1` override forces `mag_s=0`). The existing code
  clamped `k2_squared = max(0.25*s - kaon_mass**2, 0)` to zero below
  threshold, giving `k2=0` there; its `cot_delta` denominator then computed
  `max(k2, tiny)**2`, and squaring `tiny` (`~2.2e-308`) underflowed to
  exactly `0.0` in float64, producing a literal `0/0.0 = NaN` inside
  `cot_delta` that propagated through `exp_2i_delta` and the final value
  (`0.0 * NaN = NaN`, not `0.0`) despite `mag_s` itself being correctly zero.
- Above `Mprime` (only reachable with `mass_max > m_prime`, not the paper
  notebooks' default): the code had no equivalent of Laura's `eta0=1`
  override, so it kept evaluating the continued formula instead of returning
  zero.

## Fix applied

`pipi_kk_rescattering.py` now keeps the signed `k2_squared_signed =
0.25*s - kaon_mass**2` (matching Laura's `k2Square_s`, including its sign)
for `eta`, uses `k2_abs = sqrt(|k2_squared_signed|)` (matching `k2Abs_s`),
and only guards the `cot_delta` denominator against the exact `0.0` at
`m == 2*kaon_mass` (where `k2_abs` is also exactly `0`, so the guard never
changes a nonzero result). For `convention="laura"`, `eta` is forced to `1`
below `2*kaon_mass` and above `m_prime`, mirroring Laura's two explicit
override conditions; `convention="paper"` keeps the safer denominator (not
convention-specific) but not the override, since that override is a Laura++
implementation choice, not part of the printed equations.

Re-running the same 43-point grid after the fix: max `|diff|` is `8.3e-17`
everywhere, including the previously-NaN region below threshold and the
previously-unbounded region above `Mprime`.

One single-point deviation from the literal C++ is deliberate: at exactly
`m == 2*kaon_mass`, Laura's own C++ computes `0.0 * cos(2*atan(1/NaN))`
(`cotdelta0_s` is `0/0` there too, in double precision), which is itself
`NaN` — a landmine in the upstream code, not a physical feature. This
implementation instead returns the well-defined two-sided limit, `0`, at
that single measure-zero point.

## Not fixed (pre-existing, out of scope here)

`jax.grad` of `|PipiKKRescattering(...)|**2` with respect to the `mass`
*argument itself* is `NaN` exactly at the outer window edge
(`m == mass_max`), in both `"paper"` and `"laura"` conventions, before and
after this change — a generic `jnp.where`-at-a-boundary gradient artifact
(the discarded branch's gradient is finite/NaN and `0 * NaN = NaN` survives
the reverse pass) rather than anything introduced by this fix. It was
reproduced on `"paper"`, which this change does not touch. In the fit
machinery, `mass` is a data/quadrature value, not a `Parameter`; gradients
are taken with respect to fit parameters, which are not part of this
formula, so this is not expected to be reachable via `PreparedAmplitudeCache`
gradients in current usage. Left unaddressed pending an actual failure.

## Separate, notebook-level finding: default lambdaKK

`PipiKKRescattering`'s class default `delta_kk_squared=1.0` (i.e.
`lambdaKK=1.0`) does not match `LauRescatteringRes`'s own hardcoded default
`lambdaKK=2.8`; `tests/test_paper_lineshapes.py`'s reference-value test
deliberately uses the class default, not Laura's, so this default was never
intended to double as "Laura's default". The `paper_isobar_benchmark*`
notebooks construct their `rescattering` component as
`PipiKKRescattering(convention=RESCATTERING_CONVENTION)` with no
`delta_pipi_squared`/`delta_kk_squared` override, i.e. `lambdaKK=1.0`, not
Laura's `2.8`. Whether the actual Laura++ configuration that produced a
given `gen-3pi_toy*.root` set `lambdaPiPi`/`lambdaKK` explicitly or left them
at `LauRescatteringRes`'s defaults is external information this repository
does not have (the notebooks already note that `Fit3piIsobar.cc` could not be
retrieved); this is not something the formula fix above can resolve, and
should be confirmed against whatever Laura++ config actually generated the
toys before treating an ensemble parameter-recovery fit as a clean test of
this component.
